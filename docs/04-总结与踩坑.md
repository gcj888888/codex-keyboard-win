# 04 · 总结分析与踩坑记录

> 我们是怎么跑通的、踩了哪些坑、学到了什么。

## 一、全链路数据流（一句话说清楚）

```
你说一句话
  → 板子录音（16kHz PCM，每 20ms 一包）
  → Wi-Fi UDP 发给电脑上的 Host（17333 端口）
  → Host 调千问 ASR 转成文字
  → 文字投递给本地 Codex（按槽位 FIFO）
  → Codex 读文件、跑命令、调云端 qwen3-max 思考，完成任务
  → 任务完成写进"流水账"（rollout 文件）
  → Host 观察到完成 → 生成总结 → 调千问 TTS 合成语音
  → 加密后分包发回板子（AES-256-GCM，ADPCM 压缩）
  → 你按 S5，板子放出来
```

### 上行 8 环（从按键到任务入队）

| # | 环节 | 谁做 | 关键点 |
|---|---|---|---|
| 1 | 按键 → 开始录音 | 固件 | 20ms/帧，HMAC 签名 |
| 2 | UDP 发到 17333 | 固件 → Host | 走 Wi-Fi |
| 3 | 收包分流 | Host | 看包头 4 字节（EIHB/EIP*/EIAU）|
| 4 | 验签 + 查会话 + 查序号 | Host | 常量时间比较防时序攻击 |
| 5 | 收结束帧 → 交 ASR | Host | 太短（<200ms）拒收 |
| 6 | ASR 转文字 | 千问 | |
| 7 | 按槽位入队 | Host | 决定任务快慢的是**工作目录大小** |
| 8 | 启动 Codex 子进程 | Host | 四重保险（独立进程组/PDEATHSIG…）|

### 下行 9 环（从完成到播放）

| # | 环节 | 谁做 |
|---|---|---|
| 1 | 观察 rollout 流水账（20ms/轮）| Host |
| 2 | 发现 `task_complete` → 标记完成 | Host |
| 3 | 生成总结（spark，含上一条未听的合并）| Host + 千问 |
| 4 | 强校验：覆盖的 completion 必须精确匹配 | Host |
| 5 | TTS 合成语音 | 千问 |
| 6 | 加密缓存 | Host |
| 7 | 发布 → 变成 `unheard`（灯亮）| Host |
| 8 | 你按 S5 → 分包下发（窗口 6 包）| Host → 板子 |
| 9 | 播完回执 → 标记 `heard`（灯灭）| 板子 → Host |

## 二、我们踩的坑（12 条，按价值排序）

### 🥇 1. 端口漂移导致"灯永不变色"（排查一整晚）

- **现象**：按键后第 5 颗灯不变黄、按 S5 没声音。但偶尔能听到一条旧语音 → 制造"链路是通的"错觉。
- **根因**：`ECI_LAN_AUDIO_PORT` 只写在手动启动的 shell 里，**没写进 systemd 的 `Environment=`**。
  WSL 重启后服务用默认值 → 与板子 NVS 里配的端口不一致。**UDP 发错门不报错，只有超时。**
- **弯路**：用模拟器分别打两个端口做对照 —— **这个方向本身是错的**：模拟器打哪个端口是
  我自己指定的，只能证明"Host 在哪监听"，**证明不了板子往哪发**。
- **正解**：**抓包**确证板子实际发往哪个端口（`tcpdump -nn udp port 17333`）。
- **教训**：**UDP 静默失败 → 先抓包确认端口匹配，再怀疑数据格式。**

### 🥇 2. 固件编译：别去 Windows 折腾，WSL 里就有 ESP-IDF

- **现象**：在 Windows 的 `C:\esp\v5.5.5` 折腾，`idf.py build` 反复报"找不到 Ninja/编译器"，
  试了 5 种办法全卡住。
- **根因**：**方向错了**。WSL 里早就装好了完整可用的 ESP-IDF（`/root/esp-idf-local`），
  原作者的构建产物就在里面。
- **教训**：**先找现成的路（看原作者的 build 日志/产物），别凭想象造方案。**

### 🥈 3. `source export.sh` 失败，因为缺一个用不到的工具

- **现象**：报 `tool riscv32-esp-elf-gdb has no installed versions`，整个激活失败。
- **根因**：`export.sh` 做**全量工具检查**，缺一个 RISC-V 调试器就整体失败 ——
  而我们 S3 是 **XTensa 架构**，根本用不到。
- **正解**：绕过 `export.sh`，手动配 PATH。
- **教训**：全量检查失败 ≠ 环境不可用。

### 🥈 4. cmake 报 `head-ref` 缺失（空 git 仓库）

- **根因**：cmake 的 `git_describe` 需要 `.git/refs/heads/master` 存在才能生成 `head-ref`；
  "有 `.git` 但无 commit"的空仓库 → 生成失败 → 构建失败。
- **正解**：`git commit --allow-empty -m "init"`。
- **教训**：空 git 仓库会卡住依赖 `git describe` 的构建系统。

### 🥈 5. 僵尸总结锁：一次失败卡死几小时

- **现象**：总结永远出不来，日志刷 336 次 "another summary generation is already running"。
- **根因**：`publish_summary` 失败时**直接 return，忘了释放 generating 记录** → 留下僵尸 →
  后续每次重试都撞锁。
- **正解**：失败时补 `abandon(&claim)`；另加 systemd timer 兜底。
- **教训**：**拿锁的代码，任何失败路径都必须释放锁。**

### 🥉 6. 孤儿任务的"毒药 completion"死循环

- **现象**：已解绑任务遗留的 completion 被反复重试，3.8 小时刷 137 条 abandoned，白烧 token。
- **根因**：选任务的 SQL **没过滤"是否仍绑定"** → 孤儿任务被无限轮询。
- **正解**：SQL 加 `task_id IN (SELECT task_id FROM bindings)` + 连续失败熔断。
- **教训**：**重试提速必须配熔断**（单独把 30s 改 5s 会让死循环烧得更凶）。

### 🥉 7. `contains("401")` 裸数字误判

- **现象**：7 个任务 0 秒内全部失败，标着 authentication。
- **根因**：用 `text.contains("401")` 判认证失败 —— 任何含 "401" 的文本都被误判。
- **正解**：精确匹配错误码。

### 8. Host 日志完全没有时间戳

- **现象**：排查"卡了多久"时无从下手。
- **根因**：2709 行日志里只有 118 行带时间，还是别的进程写的。
- **正解**：加 `elog!` 宏替换 111 处输出。
- **教训**：**日志没时间戳 = 排查时瞎眼**，最低成本最高回报的改动。

### 9. 固件录音队列溢出会吃掉整句话

- **根因**：Wi-Fi 抖动 → 队列（64 帧=1.28s）溢出 → 丢帧 → 序号缺口 → 固件立刻作废整句。
- **正解**：队列 64→256 帧；缺口 ≤10 帧不再作废。

### 10. WSL 发行版被空闲回收，Host 一起消失

- **根因**：WSL2 空闲后回收，vmmem 退出 → systemd 服务全没。
- **弯路**：`.wslconfig` 的 `instanceIdleTimeout=-1`（实测不总能生效）。
- **正解**：`keepalive.vbs` 每 5 分钟戳一下保活。

### 11. 宿主机测试必须先 Debug 编译（自检时发现的）

- **现象**：`protocol_test.cpp` 编译失败，报一堆 `unused-parameter`（`-Werror`）。
- **根因**：我用 `-DCMAKE_BUILD_TYPE=Release` → `-DNDEBUG` 禁用了 `assert()` → 那些
  `assert(EVP_...)` 调用消失 → 参数变成"未使用" → 警告升级成错误。
- **正解**：**用默认（Debug）模式编译宿主测试**（测试依赖 assert）。
- **教训**：测试代码依赖 assert 时不能开 NDEBUG。

### 12. 源码行尾符 CRLF/LF 不统一（自检时发现的）

- **现象**：宿主测试 `firmware_source_contract_tests` 失败；补丁一开始异常大（+18000 行）。
- **根因**：原项目源码是 **LF**，我们环境的副本被转成了 **CRLF**。而测试用**精确字符串匹配**
  （含 LF 换行），CRLF 源码匹配不上；diff 也会把整个文件当成改了。
- **验证**：用**原版**跑同一个测试**也失败** → 证明不是我们的改动引起的。
- **正解**：统一为 LF + 加 `.gitattributes`；生成补丁时统一行尾符。
- **教训**：**跨平台传文件要盯住行尾符**；测试失败先分清"自己引入的"还是"原版就有的"
  （用原版跑一遍对照）。

### 13. 改了固件常量却没同步"源码契约测试"（自检时发现的）

- **现象**：修完行尾符后，测试失败点从 181 行变成 433 行 —— 暴露出一条**真正属于我们**的问题。
- **根因**：`firmware_source_contract_tests.cpp` 硬编码校验
  `constexpr std::size_t kAudioCaptureQueueFrames = 64;`，而我们把固件改成了 **256**。
  这是**防回归契约测试**：它故意盯着关键常量，防止有人误改。
- **正解**：同步更新契约期望值（64→256），并把它一起纳入 `patches/02-firmware-fixes.patch`。
- **教训**：**改固件关键常量，要连带更新契约测试**；反过来说，这类测试是项目的"护栏"，
  不该绕过 —— 它确实帮我们确认了改动位置。

### 🔬 自检方法论：两步定位法

上面 12、13 两条是同一轮自检里挖出来的，过程值得记下来：

1. **先问"是不是原版也失败"** —— 用原版跑同一个测试。若是 → 环境/原项目的坑（第 12 条）；
   若否 → 我们自己引入的（第 13 条）。这一步能立刻分锅，避免白修。
2. **修掉第一个坑后，看失败点会不会前移** —— 行尾符修完后失败点从 181 行移到 433 行，
   这正是"遮住的问题被揭开"，说明还有第二个坑。

**宿主测试正确跑法**（两个必须）：默认（Debug）模式 + 源码 LF。
```bash
cd firmware/host_test
cmake -B build -G Ninja          # ⚠️ 不要传 -DCMAKE_BUILD_TYPE=Release（会禁用 assert 导致编译失败）
cmake --build build
ctest --test-dir build
# 期望：100% tests passed, 0 tests failed out of 57
```

## 三、三条核心经验（最重要）

1. **凡事找真相源，别用推理替代它。**
   板子发哪个端口？看 NVS。任务完成没有？看 rollout。听过没有？看板子回执。
   我早期犯的最大错误，就是"逻辑上它应该发 17334"，然后改错了端口害了一整晚。

2. **UDP 是静默的 —— 抓包 > 推理。**
   发错端口不报错、丢包不报错。所有涉及网络的问题，先抓包看实际流量。

3. **测试失败先对照"原版是否也失败"。**
   这能立刻把"我引入的 bug"和"原项目的坑/环境差异"分开，避免白修。

## 四、我们修的 5 个原项目缺陷（可提给作者）

| 缺陷 | 影响 | 严重度 |
|---|---|---|
| 总结锁无超时回收 | 一次失败卡死数小时 | 高 |
| 孤儿任务毒药循环 | 无限重试烧钱数小时 | 高 |
| `contains("401")` 误判 | 任务批量假失败 | 中 |
| Host 日志无时间戳 | 排查困难 | 中 |
| 固件录音队列溢出 | 用户说话被吃掉 | 中 |
