# 03 · 云端篇 —— 云端怎么配置

> "云端"在这里指两件事：**① 千问（DashScope）提供的 ASR/TTS/大模型**、
> **② Codex 背后的模型服务**。本篇基于我们实测的配置。

## 一、云端提供什么

整套系统用到 4 个模型，全部走**阿里云百炼（DashScope）北京区**：

| 用途 | 模型 | 说明 |
|---|---|---|
| **语音识别**（你把话转文字）| `qwen3-asr-flash` | Host 调，OpenAI 兼容接口 |
| **语音合成**（把总结念出来）| `qwen-audio-3.0-tts-flash` | 音色 `longanfengyue`（龙眼凤月）|
| **Codex 的"脑子"** | `qwen3-max` | Codex CLI 通过 DashScope 调用 |
| **总结生成** | `qwen3-max`（reasoning=high）| 由 spark_runner 调 |

> 注意：**Codex 装在本地，但"脑子"在云端**。本地 Codex 负责读写文件、跑命令，
> 遇到要想的事就调用云端的 `qwen3-max`。

## 二、怎么配置 API Key

**一个 key 够用**（ASR/TTS/模型共用）。放在**仓库外**：

```bash
sudo tee -a /etc/environment >/dev/null <<'EOF'
QWEN_API_KEY=<在此填你的北京区 key>
EOF
```

获取方式：登录 [阿里云百炼控制台](https://bailian.console.aliyun.com/) → API-KEY 管理 → 创建。

> 🔒 **安全铁律**：key 不进仓库、不进日志、不进截图、不给 AI。我们的仓库里
> 所有脚本都用占位符（`sk-你的key`），**实测无任何真实 key 泄露**。

## 三、Codex 的云端配置（关键：它默认连 OpenAI）

Codex CLI 默认连 OpenAI，必须改成连千问。配置文件 `~/.codex/config.toml`：

```toml
model = "qwen3-max"
model_provider = "qwen"

[model_providers.qwen]
name = "qwen"
base_url = "https://dashscope.aliyuncs.com/compatible-mode/v1"
env_key = "QWEN_API_KEY"
```

**怎么验证配好了**：
```bash
codex exec --json --skip-git-repo-check "你好" | head -3
```
能返回 JSON（含 `thread_id`）就说明 Codex 能正常连云端。

> ⚠️ Codex 要求工作目录是"受信任目录"（有 `.git`）。没有就加 `--skip-git-repo-check`。

### 认证的小坑（我们踩过）

Host 用某种方式调 Codex 时，要求 `CODEX_HOME/auth.json` 存在。
`spark_runner.rs` 的移植补丁里做了**空 JSON 兜底**（`{}`，权限 0600）——否则调用会失败。

## 四、ASR / TTS 接口细节（我们实测的）

### ASR（语音识别）

- **端点**：`https://dashscope.aliyuncs.com/compatible-mode/v1/chat/completions`（OpenAI 兼容模式）
- **请求**：`messages` 里放音频 + `asr_options`
- **实测效果**：识别"你好，请列出当前项目里所有的源文件。" → 准确
- **音频要求**：16kHz 单声道 PCM（正好是我们上行格式）

### TTS（语音合成）

- **模型**：`qwen-audio-3.0-tts-flash`
- **音色**：`longanfengyue`
- **输出**：音频 URL（Host 下载后转成板子格式）

> 下行的完整链路：文字 → TTS 生成 48kHz 音频 → 转 IMA-ADPCM（约 4:1 压缩）→
> AES-256-GCM 加密 → 分包下发给板子。所以一段 17 秒的总结约 400KB（未压缩 PCM 是 1.6MB）。

## 五、费用（实测估算）

| 环节 | 消耗 | 成本参考 |
|---|---|---|
| ASR | 每次说话约 5~10 秒音频 | 极低（按音频时长计）|
| 总结 + TTS | 每条约 400 字 + 17 秒语音 | 低 |
| Codex 执行 | 每任务 40~50 秒、消耗 token 较多 | **主要成本在这** |

**省钱的两个关键**（我们实测的优化点）：
1. **Codex 工作目录别太大** —— 目录越大，每轮扫描读入的 token 越多。
   实测 478MB 项目 ≈ 60 秒/任务；小目录可降到 20~30 秒。
2. **别让毒药任务空转** —— 原项目有个 bug：解绑任务的残留会被无限重试，
   3.8 小时刷了 137 次，白烧 token（我们已修）。

## 六、我们实测过的新模型（Qwen-Audio 3.1 系列）

> 这一段是实测结论，供后续升级参考。**当前生产用的是 3.0 系列**。

| 模型 | 可用性（实测）| 结论 |
|---|---|---|
| `qwen-audio-3.1-asr-flash` | ✅ 可用，但**不支持 OpenAI 兼容接口** | 识别更准（能听出"rust 源文件"），带词级时间戳。换它要改调用代码 |
| `qwen-audio-3.1-tts-flash` | ❌ 报 engine error | 接口没摸通 |
| `qwen-audio-3.1-tts-next` | ✅ **可用，能生成音乐** | 参数是 `input.text_prompt`；官方定位"可生成人声/音效/环境音/音乐" |
| `qwen-audio-3.1-realtime-plus` | 存在于平台列表 | 全双工对话，需重做交互架构 |

**一个重要的方法论**：**别用平台的模型列表判断"能不能用"** —— 我们实测发现，
**正在用且工作正常的两个模型，列表里也没有**。要判断必须**真实调用一次**。

## 七、备忘：为什么下行不能播任意音乐

下行音频通路**只接受 TTS 返回的音频 URL**（`dashscope.rs` 的
`parse_batch_tts_audio_url()` 会拒绝其他来源）。

所以"让它放首歌"目前做不到 —— Codex 只会查歌曲信息、写成文字、被 TTS 念出来
（而不是真的播音乐）。要支持的话需要新增一条音频通路（我们评估过，可行但要开发）。
