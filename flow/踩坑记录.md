# 踩坑记录

## 2026-09-23 · 端口漂移导致"灯永不变色"（最坑，排查了一整晚）  [已解决]

- **现象**：板子按键后第 5 颗灯不变黄、按 S5 听不到东西；但偶尔能听到一条**旧的中文语音**，
  制造出"链路是通的"错觉。
- **触发条件**：WSL 发行版被空闲回收 → systemd 重新拉起 Host → Host 用了**默认端口**。
- **试过没用的**（关键！）：
  - 怀疑数据线/驱动 —— 无用，板子 USB 枚举正常
  - 怀疑固件坏了 —— 无用，重烧也没用
  - 用模拟器打两个端口做对照 —— **这个方法本身是错的方向**：模拟器打哪个端口是我自己指定的，
    它只能证明"Host 在哪监听"，**证明不了板子往哪发**
- **根因**：`ECI_LAN_AUDIO_PORT` 只写在手动启动的 shell 里，**没写进 systemd 的 `Environment=`**。
  WSL 重启后服务用默认值生效 → 与板子 NVS 里配的端口不匹配。
  UDP 无连接，**发错门不报错，只有超时**。
- **解决**：端口写死进 service 文件；用**抓包**确证板子实际发往哪个端口
  （`tcpdump -nn -i any udp port 17333`）。详见 `scripts/wsl/install-service.sh`。
- **教训**：**UDP 静默失败时，先抓包确认端口匹配，再怀疑数据格式**。真相源是板子 NVS 的配置，
  不是"逻辑上它应该发哪"。

## 2026-09-23 · 固件编译：别去 Windows 折腾，WSL 里就有 ESP-IDF  [已解决]

- **现象**：想编译固件，先在 Windows 的 `C:\esp\v5.5.5` 折腾，`idf.py build` 反复报
  "找不到 Ninja / 找不到编译器"，试了 5 种办法（手动 PATH、显式指定 ninja、dot-source 激活脚本…）
  全卡在同一个点。
- **根因**：**方向本身就错了**。WSL 里早就装好了完整可用的 ESP-IDF（`/root/esp-idf-local`），
  原作者的构建产物就在 WSL 里。
- **解决**：在 WSL 里编译 ——
  ```bash
  export IDF_PATH=/root/esp-idf-local
  export IDF_TOOLS_PATH=/root/.espressif
  export PATH="/root/.espressif/python_env/idf5.5_py3.14_env/bin:/root/.espressif/tools/xtensa-esp-elf/*/xtensa-esp-elf/bin:$PATH"
  python /root/esp-idf-local/tools/idf.py build
  ```
- **教训**：**踩空前先找现成的路**（原作者的 build 目录、日志就是证据），不要凭"想当然"造方案。

## 2026-09-23 · `source export.sh` 失败？因为缺一个用不到的工具  [已解决]

- **现象**：`source /root/esp-idf-local/export.sh` 报
  `tool riscv32-esp-elf-gdb has no installed versions`，然后整个激活失败、PATH 没配好。
- **根因**：`export.sh` 会做**全量工具检查**，缺一个 RISC-V 芯片用的调试器就整体失败 ——
  而 ESP32-S3 是 **XTensa 架构**，根本用不到 riscv 工具。
- **解决**：**绕过 `export.sh`，手动配 PATH**（见上一条）。编译只需 xtensa 工具链 + python env。
- **教训**：全量检查失败 ≠ 环境不可用。看它缺的到底是什么。

## 2026-09-23 · cmake 报 `head-ref` 缺失，因为 git 仓库是空的  [已解决]

- **现象**：cmake 配置阶段报
  `CMake Error at grabRef.cmake:48: file failed to open .../head-ref`，构建直接失败。
- **根因**：cmake 的 `git_describe` 需要 `.git/refs/heads/master` 存在才能生成 `head-ref`；
  而本仓库是"有 `.git` 但没有任何 commit"的空仓库 → `master` 分支 ref 文件不存在 → 生成失败。
- **解决**：建一个空 commit：`git commit --allow-empty -m "init-for-fw-build"`。
  已内建进 `scripts/wsl/flash-firmware.sh`。
- **教训**：空 git 仓库（无 commit）会卡住依赖 `git describe` 的构建系统。

## 2026-09-23 · 僵尸总结锁：一次失败卡死几个小时  [已解决]

- **现象**：总结永远生成不出来，信箱灯不亮、按 S5 没声音；日志刷 336 次
  "another summary generation is already running"。
- **根因**（读源码定位）：`summary_orchestrator.rs` 里 `publish_summary` 失败时**直接 return，
  忘了释放那条 generating 记录** → 留下僵尸 → 后续每次都撞锁。
- **解决**：发布失败时补 `self.abandon(&claim)`。另加 systemd timer 每 2 分钟兜底清理
  （`tools/clean_interrupted.py`）。
- **教训**：**拿锁的代码必须保证任何失败路径都释放锁**；外部看门狗只是兜底，治标不治本。

## 2026-09-23 · 孤儿任务的"毒药 completion"死循环  [已解决]

- **现象**：某个已解绑任务遗留的 completion 被反复重试，3.8 小时内刷了 **137 条 abandoned**，
  白白烧 token。
- **根因**：`store.rs::summary_work_tasks_after` 选任务时**没过滤"是否仍绑定"** →
  任务换绑后成孤儿，其未总结的 completion 被无限轮询、每次都被模型拒绝。
- **解决**：SQL 加 `AND task_id IN (SELECT task_id FROM bindings)`；另加"连续失败 5 次熔断"。
- **教训**：**重试提速必须配熔断**——单独把重试从 30s 提到 5s，会让毒药循环烧得更凶。

## 2026-09-23 · `contains("401")` 裸数字误判  [已解决]

- **现象**：7 个任务在 0 秒内全部 `exit_failure`，原因标着 `authentication`。
- **根因**：`codex_runner.rs` 用 `text.contains("401")` 判断认证失败 ——
  任何含 "401" 的文本（比如某行日志、某个数字）都会被误判。
- **解决**：改成精确匹配错误码。
- **教训**：**不要用裸子串匹配错误码**。

## 2026-09-23 · Host 日志完全没有时间戳  [已解决]

- **现象**：排查"卡了多久"时发现无从下手 —— 日志里看不出时间。
- **根因**：Host 所有 `eprintln!` 都没带时间戳（2709 行里只有 118 行以 `[` 开头，还是别的进程的）。
- **解决**：`lib.rs` 加 `time_stamp()` / `elog!` 宏，替换 111 处输出。
- **教训**：**日志没有时间戳 = 排查时瞎眼**。这是最低成本、最高回报的改动。

## 2026-09-23 · 固件录音队列溢出会吃掉整句话  [已解决]

- **现象**：说了较长的话，Host 只收到半句或整句被丢弃。
- **根因**：Wi-Fi 抖动 → 麦克风采集队列（64 帧 = 1.28 秒）溢出 → 丢帧 → 序号出现缺口 →
  固件立刻作废整次录音。
- **解决**：队列 64→256 帧（5.12 秒）；缺口 ≤10 帧不再作废，交给 Host 补静音。
- **教训**：实时音频"宁可补静音也别丢整句"，但容忍要有上限（Host 侧已有 `MAX_CAPTURE_GAP_FRAMES=10` 对齐）。

## 2026-09-23 · WSL 发行版被空闲回收，Host 跟着一起消失  [绕道解决]

- **现象**：隔一段时间板子就"不理人"，一查 Host 没在跑。
- **根因**：WSL2 发行版空闲后会被回收，vmmem 退出 → 里面的 systemd 服务全没。
- **试过没用的**：`.wslconfig` 里 `instanceIdleTimeout=-1`（实测不总能生效）。
- **解决**：`scripts/windows/keepalive.vbs` 每 5 分钟戳一下 WSL 保活（放启动目录）。
- **教训**：WSL 不是"永远开着"的环境，常驻服务要有保活措施。

## 2026-08-10 · 不要把“声音”默认理解为电脑系统音量

- 现象：用户要求旋钮调音量时，曾错误实现成 USB/BLE 系统音量键，但产品真正要调的是键盘板载扬声器。
- 根因：没有先明确声音的所有者，直接沿用了普通键盘旋钮最常见的 Consumer Control 方案。
- 约束：以后涉及音量、播放、静音，先写清 `Mac / 手机 / 键盘扬声器` 三者中的唯一目标，再改协议。
- 验证：板载音量必须在固件 PCM 写入点生效，并以真机旋转、短按播报、播放中调整和重启保持验收；
  Mac 音量不变只作为辅助反证。

## 2026-08-10 · 短按提示音不能依赖开机音已经初始化扬声器

- 现象：直接调用嵌入音频播放在“开机音被麦克风抢占或深睡唤醒后跳过”时可能返回 not ready。
- 根因：正常开机音路径会初始化 SpeakerOutput，但这不是短按功能可以依赖的产品前置条件。
- 修复：短按时若扬声器未就绪，且启动资源阶段已经 Ready，则先拉起 SpeakerOutput，再提交嵌入音频。
